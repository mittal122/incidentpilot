⛑ incidentpilot — Technical Architecture

An AI incident-response platform for Kubernetes: alerts are detected and enriched by the alert pipeline, investigated by the IncidentChat AI engine, and presented — with human-approved remediation — in a purpose-built ops console.

1. Agent Architecture

The system has one true AI agent plus two non-LLM automation actors and a human approval gate. We describe it honestly as a hybrid agent architecture — LLM reasoning where judgment is needed, deterministic code where reliability is needed.

🤖 IncidentChat AI engine — the investigator (LLM agent)

Responsibility: root-cause analysis. Given an alert or a free-form question, it runs an agentic tool-use loop: the LLM chooses tools (kubectl queries, pod logs, Prometheus metrics, Loki log search), reads the results, chooses again, and finally writes an explanation with evidence and a suggested fix. It is the only component that "thinks."

⚙️ Alert pipeline runner — the reflex agent (rule-based, no LLM)

Responsibility: detection, enrichment, routing, and narrowly-scoped auto-remediation. It watches the Kubernetes API directly (via kubewatch) and receives Prometheus alerts, attaches context (pod logs, events, restart counts), fans findings out to sinks (Slack, the console webhook), and executes playbooks — e.g. auto-delete crash-looping pods, but only in namespaces prefixed robusta-test.

🖥 Console — the orchestrator & approval gate (our code)

Responsibility: the human interface. Stores incidents, renders dashboards, proxies questions to the AI engine, renders AI answers as rich UI, executes human-approved actions (restart pod) through the Kubernetes API, and manages which LLM provider the AI engine uses.

Why hybrid instead of a single do-everything agent?

Reliability: detection must never miss an event; rule-based watchers are deterministic and cheap, while an LLM in the detection path would add latency, cost, and hallucination risk to the one stage that must be exact. Cost & latency: the LLM is invoked only when a human asks "why?" — not on every cluster event. Safety: mutations go through exactly one audited code path with human approval; the LLM can read everything but change nothing. Each actor does what its substrate is best at.

2. Application Flow

Flow A — an incident happens (push path)

  1. A pod in any namespace fails — e.g. crashes on startup because its database password is wrong → Kubernetes marks it CrashLoopBackOff.
  2. Detection: the alert pipeline's kubewatch sees the pod-state change within seconds (Prometheus alert rules fire in parallel for metric-based conditions and reach the alert pipeline through Alertmanager).
  3. Enrichment: the alert pipeline runner builds a finding: title, severity, subject (namespace/pod/kind), recent logs, events.
  4. Fan-out: the finding goes to Slack and is POSTed as JSON to the console's /api/ingest; the console stores it in SQLite.
  5. Display: the Overview card grid and Incidents table (htmx, polling every 5–10 s) show the incident — critical namespaces sort first.
  6. Investigation (on demand): the user clicks Investigate with the AI engine. The console composes a prompt from the stored finding and calls the AI engine' /api/chat with the active model alias.
  7. Agentic loop: the AI engine' LLM iterates: list pods → describe pod → fetch logs → (optionally) query Prometheus/Loki — each round is one LLM call choosing the next tool — then writes a root-cause analysis in Markdown.
  8. Rendering: the console converts the Markdown to sanitized HTML (tables, code, colored status chips) and stores the analysis with the incident.
  9. Remediation: if appropriate, the user clicks Approve: restart pod. The console validates the names against a strict regex and runs kubectl delete pod; the pod's Deployment recreates it. Nothing is ever executed without that click (outside the one whitelisted test-namespace playbook).

Flow B — the user asks a question (pull path)

  1. User types into Ask the AI engine: "Which pods are unhealthy right now?" (htmx form POST to the console).
  2. The console appends a formatting hint (bold one-line summary first, tables for resources) and forwards to the AI engine with the active provider's model.
  3. the AI engine runs the same tool loop against the live cluster — the answer reflects reality at that moment, not a cached index.
  4. The response is Markdown-rendered, sanitized, badge-decorated, and appended to the chat log as a rich card.

Flow C — logs with AI explanation

From any namespace page: View Logs → raw kubectl logs --tail=500 in a color-coded terminal view (filter, copy, auto-refresh, previous-run for crashed containers). The AI Summary tab sends the last 200 lines to the AI engine (tools disabled — pure summarization) and renders a sectioned explanation: Summary / Key events / Warnings / Errors / Recommended actions.

5. Agentic Framework

No external agentic framework — no LangChain, LangGraph, CrewAI, or AutoGen anywhere in the stack.

What we use instead

The IncidentChat AI engine has a purpose-built agentic loop (source under vendor/): litellm for provider-agnostic LLM calls, a curated registry of DevOps toolsets (kubectl, Prometheus, Loki, bash) exposed to the model as function-calling tools, iterative call→observe→call orchestration with token budgeting, and Kubernetes-aware system prompts refined against real incidents.

Why not LangChain / CrewAI?

Three reasons. (1) Nothing missing: the loop the AI engine implements — tool selection, iteration, structured output — is exactly the part frameworks abstract, already done, domain-tuned. (2) Fewer layers: frameworks add their own abstractions (chains, graphs, crews) between you and the LLM call; when an investigation misbehaves we read one loop in one file, not framework internals. (3) Single-agent reality: multi-agent frameworks earn their complexity when multiple LLM agents negotiate; our architecture intentionally has one reasoning agent surrounded by deterministic actors — a message-passing framework would be scaffolding with nothing to scaffold.

Console-side "orchestration" is deliberately plain code: a webhook handler, an HTTP proxy, and a rendering pipeline — readable in one sitting.

6. Purpose of the Application

The problem

When production breaks, engineers burn the first 20–40 minutes on archaeology: which pod, since when, what do the logs say, what changed. The evidence is scattered across kubectl, Prometheus, Loki, and Slack — and the person on call at 3 a.m. may not know the failing service.

What IncidentPilot does

FeatureValue
Namespace card overview, critical-firstCluster health in one glance; the worst problem is the first card
Auto-captured, enriched incidentsNo more "when did this start?" — the timeline builds itself
One-click AI root-cause investigationMinutes of kubectl archaeology → one button; answers cite actual log lines
Ask the AI engine chatPlain-language questions against the live cluster
Logs with AI explanationRaw terminal view for experts, plain-English summary for everyone else
Human-approved remediationFix from the same screen — with a person, not a model, pulling the trigger
Provider settingsSwap the AI brain (5 providers) at runtime from the UI

Audience & differentiation

Small platform/DevOps teams and solo developers running Kubernetes. Versus existing tools: k9s/Lens show state but don't explain it; Datadog/New Relic explain more but are closed and priced per host; the alert pipeline's own SaaS dashboard is the closed piece of an otherwise open stack. IncidentPilot is the missing open-source layer: the full detect → explain → approve → fix loop, self-hosted, with the LLM provider under your control.

7. Overall Architecture

The system in one paragraph

Applications run; Prometheus and kubewatch notice when they misbehave; the alert pipeline enriches each event into a finding and pushes it to Slack and the console; the console stores and displays it as a live, critical-first health dashboard; when a human wants to know why, one click sends the context to the IncidentChat AI engine, which investigates the actual cluster with real tools and returns an evidence-backed root cause rendered as rich UI; and when the fix is a restart, the human approves it and the console executes one validated kubectl command. The AI reasons, the rules react, the human decides.

Repo layout: vendor/ holds third-party component sources; console/ is our code (~700 lines Python, 8 templates, one stylesheet); deploy/ holds Helm value examples; ./run.sh boots everything locally. Secrets live only in cluster-side Helm values / ConfigMaps, never in the repo — which is what keeps the project safely open-sourceable.
